# Phase 12 — UI Design Contract

> Visual and interaction contract for the panel's **hotspot editor** — the SVG polygon draw/edit/delete
> surface at `proyectos/[id]/hotspots`. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> This phase **inherits the panel design system settled in Phase 10 and reused in Phase 11** (hand-rolled
> ImBau tokens, no shadcn, no component library — `packages/ui/src/tokens.css` is the reconciled source of
> truth carrying palette + neutrals + type scale + radii; the Tailwind v4 `@theme` mirror + `next/font`
> wiring already live in `apps/panel`). Phase 12 is a **third sibling styled surface** to the units grid
> (10) and leads bandeja (11): it reuses the same tokens, wiring, two-weight system, and inline
> `role="status"`/`role="alert"` feedback pattern (no global toast — Phase 10 D-04), and only specializes
> the **component + copy + interaction** contract for a direct-manipulation SVG canvas.
>
> UI copy is **es-AR, voseo**, product tone (CLAUDE.md, brand-book §Voz). Panel is **desktop-first** (a
> visual authoring tool that needs pointer precision for vertex dragging — mouse is the primary input).
> Persisted geometry is **viewBox-intrinsic (0–1000), never pixel-bound** (D-09) — the canonical
> representation never depends on the on-screen render width, exactly as money is whole-integer never float.

### Wiring (already established — do NOT re-invent)

The panel adopted the Tailwind v4 CSS-first + `@theme` mirror pattern in Phase 10 (`apps/panel/app/globals.css`
mirrors `@imbau/ui/tokens.css`; the three `next/font` variables are set on `<html>` in
`apps/panel/app/layout.tsx`). Phase 12 consumes that as-is — no new token file, no new font wiring. Use the
un-prefixed tokens (`--grafito`, `--cobre`, `--blueprint`, `--gris-500`, `--radius-md`, `--text-*`); do not
fork to `--imbau-*`.

### RSC spine (inherited from Phase 9/10 — clone, do not reinvent)

The hotspots tab body replaces only the placeholder in `apps/panel/app/proyectos/[id]/hotspots/page.tsx`.
Same server spine as the unidades tab: `await params` → `z.uuid()` guard → `notFound()` →
`resolveProject` (RLS-scoped, cached) → `notFound()` → `canWrite` from `resolveActiveRole()`. The interactive
canvas is a `"use client"` island wired via `useTRPC`; **the server `requireRole("owner","developer")` on the
save/delete mutations is the authority** — the client draw affordances being visible is cosmetic.

is not used).

| sm | 8px | List-item vertical padding, compact toolbar control gaps |
| lg | 16px | Default element spacing, toolbar padding, selector-panel item gaps, canvas inset from panel |
| xl | 24px | Section padding, selector-panel body padding, modal body padding |
| 2xl | 32px | Page gutter, canvas ↔ selector-panel gutter |
| 3xl | 48px | Page-level top spacing |

Canvas / editor-specific fixed dimensions (multiples of 4):

| Element | Value |
|---------|-------|
| Selector panel width (floors / units list, left rail) | 280px |
| Editor toolbar height | 48px |
| Breadcrumb / mode bar height | 44px |
| Vertex handle visual diameter | 12px |
| Vertex handle hit target (invisible, centered on handle) | 24px |
| Vertex / polygon stroke width | 2px |
| Active-vertex focus ring | 2px |
| Selector list-item height | 44px (comfortable click target for drill-down) |
| Button height | 40px |
| Has-polygon indicator dot | 8px |

Exceptions: the **24px vertex hit target** is deliberately larger than the 12px visual handle so a vertex
stays grabbable without visually crowding a dense polygon — this is a pointer-precision affordance, not a
spacing violation (both values are multiples of 4).

## Typography

Inherited from Phase 10/11 — the same **two-weight system**: **400** for all Inter text/UI/lists/toolbar and
JetBrains Mono figures; **500** for the Space Grotesk H1 only. Emphasis via size + color hierarchy
(Grafito vs Gris-500), never via weight.

| Role | Size | Weight | Line Height | Family |
|------|------|--------|-------------|--------|
| List meta / dense (has-polygon hint, vertex count) | 14px (0.875rem) | 400 | 1.3 | Inter |
| **Figures** (vertex coords, vertex count, viewBox readout) | 14px (0.875rem) | 400 | 1.2 | **JetBrains Mono, `tabular-nums`** |
| Selector item label (`Piso 4`, `Unidad 4B`) | 16px (1rem) | 400 | 1.3 | Inter (emphasis via Grafito color + size, not weight) |
| Body / labels / controls / instructions | 16px (1rem) | 400 | 1.5 | Inter |
| Panel section heading (`Pisos` / `Unidades`) · toolbar mode label | 20px (1.25rem) | 400 | 1.25 | Inter (emphasis via size + Grafito) |
| Page title (H1: "{Proyecto} · Hotspots") | 28px (1.75rem) | 500 | 1.2 | **Space Grotesk** |

Two weight values total (400 and 500). No other weights or families permitted this phase.

**Figure rendering rule:** vertex coordinates and viewBox readouts are integers in the 0–1000 intrinsic
space, always JetBrains Mono `tabular-nums` so they don't jitter while dragging. Never render fractional
pixel coordinates in the UI — the persisted and displayed geometry is the intrinsic integer coordinate (D-09).

## Color

Panel is a light-surface data tool (brand permits: "el panel de autogestión puede ser claro"). Palette
inherited verbatim from Phase 10/11 / `tokens.css`. The one net-new usage this phase is **Blueprint as the
semantic geometry color** for drawn polygons — this is exactly what Blueprint is reserved for in the brand
book ("detalle técnico, links, **datos**"), and it does not collide with anything else on this screen
(no unit-estado dots, no pipeline-stage dots appear in the hotspot editor).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Hormigón `#F2EFE9` (app canvas + panel bg) + Blanco `#FFFFFF` (selector cards, toolbar, modals). The **render image itself** (photographic exterior / planta) occupies the canvas area — it is content, not a palette surface. | Backgrounds and selector surfaces |
| Secondary (30%) | Gris-100 `#E5E2DB` (borders, toolbar bg, panel dividers) · Gris-500 `#6B7480` (meta/secondary text, un-drawn hint) · Grafito `#14181E` (primary text) | Structure, dividers, non-primary text |
| Accent (10%) | Cobre `#D98A4F` | See reserved list below |
| Destructive / error | Vendido `#D65454` | Invalid-polygon stroke + validation banner + save/load error affordances + `Borrar polígono` confirm |

**Geometry semantic colors (reserved to the SVG overlay — NOT part of the 10% accent).** These are the
polygon-rendering palette; like the estado/stage dots in Phases 10/11 they are *status/data*, not *action*:

| Geometry state | Color | Meaning |
|----------------|-------|---------|
| Saved / idle polygon (unselected) | Blueprint `#4C7DF0` (2px stroke, ~12% fill) | An existing, persisted hotspot polygon |
| Close-the-polygon target (first vertex while drawing, hoverable to close) | Disponible green `#2FA26E` | "Podés cerrar acá" — go/valid affordance |
| Invalid polygon (degenerate / self-intersecting, during draw or edit) | Vendido red `#D65454` (2px stroke) | Blocks save (D-08) — paired with the validation banner |
| Has-polygon indicator (selector list dot) | Disponible green `#2FA26E` | Floor/unit already has a polygon drawn |

**Accent (cobre) reserved for — explicit list (this phase):**
- Primary action buttons: `Guardar polígono`, and the `Confirmar` of the delete-confirmation prompt.
- The **selected/active polygon** stroke + its draggable **active vertex handles** and the focus ring on the
  vertex currently being dragged (cobre = the thing you are acting on).
- The focused-control ring inside the toolbar / selector (2px cobre outline).

Cobre is **never** a page/large-area background, **never** a fill over the render, **never** used for the
idle/saved polygon geometry (that is Blueprint), and **never** on the selector list rows. One cobre emphasis
per active flow — the polygon you are editing.

> ⚠ **Warm-color adjacency (inherited caution):** the render is a full-color photograph; a cobre selected-
> polygon stroke could get lost over warm brick/wood renders. Mitigation: the selected polygon renders cobre
> stroke **plus** cobre vertex handles at 12px with a 2px ring and a subtle contrasting halo (1px Grafito/white
> outline under the stroke) so it reads over any render. Idle polygons stay Blueprint. Invalid stays Vendido
> red. Keep the three geometry states unambiguous against photographic backgrounds.

Links (breadcrumb "← Proyectos", the "Exterior" drill-up crumb): Blueprint `#4C7DF0`.

### Validation messages — **blocking, es-AR, no autocorrect (D-08)**

Shown in the validation banner (Vendido red) and block `Guardar polígono` until resolved. Validation is pure
(the geometry module) and runs before the mutation.

| Rule | Copy |
|------|------|
| Fewer than 3 vertices | `Un polígono necesita al menos 3 vértices.` |
| Zero / near-zero area (collinear vertices) | `El polígono no tiene área — los vértices están alineados. Movelos para que encierre una región.` |
| Self-intersecting edges | `El polígono se cruza consigo mismo — corregilo antes de guardar.` |
| Save blocked hint (button disabled while invalid) | `Corregí el polígono antes de guardar.` |

### Destructive / irreversible actions this phase

**One destructive action: `Borrar polígono` (D-02).** Clears the `poligonoSvg` field on the `floors`/`units`
row (an edit of the record, not a row delete) — irreversible from the UI (no undo/history, D-10 deferred).
It **must** be gated by a confirmation and styled with the Vendido-red destructive treatment (not a cobre
primary):

| Element | Copy |
|---------|------|
| Delete confirmation heading | `¿Borrar el polígono de {label}?` |
| Delete confirmation body | `El explorador va a dejar de mostrar este hotspot hasta que lo vuelvas a dibujar. No se puede deshacer.` |
| Delete confirm / cancel | `Borrar polígono` (red) / `Cancelar` |
| Delete — success (inline `role="status"`) | `Borraste el polígono de {label}.` |

Re-drawing over an existing polygon and saving is **not** treated as destructive-confirm: the canvas is a
live WYSIWYG preview (unlike the blind money ops of Phase 10, the change is visually self-evident), so
`Guardar polígono` overwrites without a preview modal. Only outright deletion is confirm-gated.

## Interaction Contracts

**Draw a polygon (HSPOT-01/02, D-07, D-09).** Choose a target from the selector rail first (floor in exterior
mode, unit in planta mode) → the canvas enters `drawing`. **Click** places each vertex in screen space; the
handler immediately maps the pointer to intrinsic viewBox coords (0–1000) — nothing is ever stored in pixels.
The **first vertex** renders as a green close-target; clicking it (or **double-click** anywhere) closes the
polygon. `Descartar` abandons the in-progress shape. Closing does not save — it hands off to validation +
`Guardar polígono`.

**Edit a polygon (HSPOT-03, D-01).** Click an existing (Blueprint) polygon to select it → it turns cobre and
its vertices become draggable handles. **Drag** a vertex to move it (live coord readout in mono updates);
**right-click / delete-vertex control** removes a single vertex; the whole polygon is removed via
`Borrar polígono` (see destructive gate). `Cancelar` reverts to the last saved geometry.

**Explicit save + blocking validation (D-08, D-10).** `Guardar polígono` runs the pure geometry validation
(≥3 vertices, non-degenerate area, no self-intersection) **before** the single mutation. Invalid → the
validation banner shows the specific es-AR reason, the polygon strokes Vendido red, and the button stays
disabled; **no autocorrect**, no silent fix. Valid → one mutation via the inherited
`requireRole("owner","developer")` + `withTenant` mold (clone of `projects.updateSettings`), writing the SVG
string into `floors.poligonoSvg` / `units.poligonoSvg` (**zero schema migration** for the polygon itself,
HSPOT-04) → `saving` → success (`role="status"`) or error (`role="alert"`, geometry preserved for retry).

**Drill-down mirrors the explorer (D-03/D-04).** Clicking a floor's polygon on the exterior opens that
floor's planta to draw its unit polygons — mirroring the phase-2 explorer's exterior → piso → planta → unidad
mental model. The **always-visible floor list** (safety net) lets the operator open *any* planta directly,
including a floor whose exterior polygon doesn't exist yet — resolving the chicken-and-egg (you can't click a
polygon you haven't drawn). The `Exterior` breadcrumb crumb drills back up.

**Missing render = empty state, never draw over void (D-05/D-06).** This phase assumes renders already exist
(uploaded via the media pipeline — out of scope). If the exterior render (project) or a planta render (floor)
is absent, the canvas shows the corresponding empty state and offers no drawing surface. *(Where the exterior
render is stored — a `projects` field vs a designated `media` row — is the open Research flag resolved at
planning; the UI contract only requires the canvas to receive a render URL and to show the empty state when
there is none, regardless of storage.)*

**Intrinsic coordinates are the contract with phase 2 (D-09, HSPOT-04).** Everything persisted is viewBox
0–1000; the canvas transforms screen↔viewBox on every pointer event. The stored SVG string is consumed
**as-is** by the phase-2 explorer via the existing anon policies (`floors_anon_published` /
`units_anon_published`) — the executor documents the exact string format chosen (Claude's discretion:
`<polygon points>` vs `path d`) so phase 2 parses it without ambiguity.
